# 用户错误注入器：设计（草案，2026-11-09）

状态：**草案，待讨论**。还没有实现，也没有跑过。本文只定"注入器做什么、不做什么、怎么自动验"，不定训练配置。

设计讨论的来源是 vault 文档《方法设计讨论-评审GPT方案与重新推导-2026-11-02》第 4、7.6、7.7 节；官方做法的核查见
7.7（AgentNoiseBench 的 τ² 代码）。

## 1 要解决的问题（一句话）

现有环境里，"用户确信地说出一个错误的事实"几乎不存在：官方 164 题里这类题是个位数，我们 99 题训练集里只有 2 题，而且其中 一题核对了也不加分（断言写在
`nl_assertions`，而 `reward_basis` 不含 `NL_ASSERTION`）。注入器把这类情形变成**可控、可记录、 可自动验证**的环境变量。

## 2 不变量（注入器绝不动的东西）

| 不动                                   | 为什么                                                               |
| -------------------------------------- | -------------------------------------------------------------------- |
| 任务目标、gold actions、`reward_basis` | reward 口径一变，训练前后和跨方法的分数就不可比                      |
| 数据库初始状态                         | 数据库是"真值"的唯一来源。改库等于让核对失效（见 §3 的方向性）       |
| 官方用户 guideline（全局 prompt）      | AgentNoiseBench 改的是这一份；我们改单题剧本，才能逐题记录注入了什么 |
| agent 侧的 prompt 与工具               | 否则无法区分"环境变难"和"提示词变好"                                 |

## 3 注入的方向与硬条件

注入只改**单题用户剧本里的一个字段值**：剧本让用户说出 $v_{bad}$，而数据库里仍是 $v_{true}$。

**硬条件（可程序化检查，注入前必须通过）：**

1. **真值可查**：存在一个读工具调用序列，从 `known_info` 出发可达，其返回包含 $v_{true}$。查不到就不注入。
1. **错值合法**：$v_{bad}$ 取自同一字段在数据库里的其它取值（另一条记录的地址、另一个合法的乘客数），不是格式错误的垃圾值。
   格式一眼能看穿的错值训练的是"校验格式"，不是"核对事实"。
1. **错值不等于真值**，且不在用户剧本里以其它方式泄露。
1. **方向固定**：只改用户侧。反向（改库、用户是对的）属于另一类问题，不在本注入器范围内。

**可注入字段按"真值在哪"划分**（下表的判断依据是标准答案里的写操作参数和剧本原文，已核对 retail 的 24 道改地址题）：

| 类别                     | 例子                                                               | 可注入                             |
| ------------------------ | ------------------------------------------------------------------ | ---------------------------------- |
| 库中有真值的既有事实     | 订单号、预订号、用户 id/邮编、在档地址、已订航线、乘客数、会员等级 | ✅                                 |
| 只有用户知道的意图       | 想改成什么、新地址、偏好、预算                                     | ❌ 注入即无解                      |
| 库中有真值但剧本故意不说 | retail 约 19 题的"新地址在我另一个订单里"                          | ✅（这类正是诱发模拟器编造的场景） |

## 4 改口条件（剧本里必须写明）

官方题的三种写法对应三种被训练出来的行为，这是注入器的第一个旋钮：

| 代号            | 剧本规定                               | 官方原型                                               | 训练出的行为                         |
| --------------- | -------------------------------------- | ------------------------------------------------------ | ------------------------------------ |
| `R-never`       | 永不改口                               | airline:256 "do not correct yourself"                  | agent 必须自己查库并以库为准         |
| `R-on-evidence` | agent **说出正确值**后才承认           | airline:2 "willing to admit if the agent corrects you" | 查库 → 用证据纠正用户（**主设置**）  |
| `R-on-ask`      | agent 只要说"请再确认"就自己报出正确值 | retail:46、airline:38                                  | 只需多问一句，不必查库（**对照组**） |

`R-on-ask` 作为对照是有信息量的：如果它同样把分数拉高，就说明"注入有效"可以被"学会追问"解释，而不是"学会核对"。

## 5 可解性验证（注入前，自动）

对每个候选注入跑一次检查，全部通过才进入题池：

1. **真值可达**：在该题自己的数据库上调用读工具，断言返回里含 $v_{true}$（条件 1 的实现）。
1. **gold 不受影响**：重放 gold actions，得分仍为 1；空轨迹得 0；去掉任一 gold 写操作得 0。沿用
   `scripts/tau2/check_task_pack.py` 的三项。
1. **错值会致错**：把 $v_{bad}$ 代入受影响的写操作参数后重放，得分必须变成 0。**这一条是注入有意义的充分条件**—— 如果代入错值还能满分，说明该字段
   reward 不读，注入了也没有信号。
1. 第 3 条同时是"检查能变红"的自检：对一个真值字段跑第 3 条，必须失败。

AgentNoiseBench 在 Eq. 1 里写了 $\mathbb I_{solvable}=1$ 但全文没说怎么算；上面 1–3 是我们能程序化算的版本。

## 6 注入记录（溯源）

每道注入题产出一条记录，和题一起存；每个 episode 另存实际触发情况。

```json
{"task_id": "retail:33", "variant_id": "retail:33#inj1",
 "field": {"name": "order_address1", "locator": "get_order_details(#W5918442).address.address1"},
 "true_value": "517 Lakeview Drive", "injected_value": "144 Lakeview Drive",
 "value_source": "retail task 101 same field", "recant": "R-on-evidence",
 "affected_gold_actions": ["modify_user_address"],
 "checks": {"true_value_reachable": true, "gold_replay": 1.0, "bad_value_replay": 0.0},
 "seed": 43, "generator": "<commit>"}
```

记录的用途按优先级：

1. **算检出率**（§7）——没有记录就只能靠 LLM 评判，判别器召回率只有 69%。
1. **按注入条件重加权**：episode 级、动作无关的 spec 才可重加权（Agent-Reflex 的 `noise_rollout` 门控是合法的，
   事件级触发记录不是）。
1. critic 的特权输入（优先级最低；特权 critic 已经读用户剧本 z，加这个几乎不需要改代码）。

**不进入 reward，也不进入 actor 输入。** 前者把被研究的现象变成超参，后者在部署时不存在对应标记。

## 7 指标

| 指标           | 定义                                                                                               | 为什么要它                                                       |
| -------------- | -------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 得分           | 官方 reward，不改口径                                                                              | 和基线、同行可比                                                 |
| **检出率**     | 在第一次用到字段 $f$ 的写操作之前，agent 的某次读工具返回包含 $v_{true}$，且最终库内不含 $v_{bad}$ | 程序化可算，不需要判别器                                         |
| **冗余核对率** | 干净题（未注入）上，agent 对已给事实发起的额外读工具调用次数 / 写操作数                            | 堵"全都查一遍"这个退化解：只报检出率，一个无脑全查的策略就能刷满 |
| 轮数与截断率   | 每 episode 轮数、撞 `max_steps` 比例                                                               | 核对的代价是悬崖（截断即 0 分），不是斜坡                        |

## 8 旋钮与留出

| 旋钮       | 取值                                     | 备注                                    |
| ---------- | ---------------------------------------- | --------------------------------------- |
| 注入率 $p$ | 0 / 0.25 / 0.5                           | $p$ 是定理 1 里决定 $D(p)$ 符号的那个量 |
| 改口条件   | `R-never` / `R-on-evidence` / `R-on-ask` | §4                                      |
| 字段集合   | 训练集与测试集不完全相同                 | 见下                                    |
| 每局注入数 | 1（先固定）                              | >1 会和"多错误交互"混在一起             |

**留出设计**：题目、数据库、reward 全部不变，只在注入这一维留出。

- 同分布测试：训练用的字段与改口条件。
- 留出测试：训练没出现过的字段（例如训练只注入订单号与地址，测试加入会员等级、乘客数）。
- 留出掉分有两种解释（没泛化 / 该字段更难查）。为了只留下第一种，留出字段要和训练字段**配平查询深度**： 记录每个字段"从 `known_info`
  到真值"的最短读工具调用数，训练与留出的分布对齐。

## 9 三张测试表

| 测试                                       | 回答                                                     |
| ------------------------------------------ | -------------------------------------------------------- |
| 官方干净 test（60 题）                     | 多核对有没有在正常题上掉分                               |
| 我们的注入版 test（同样 60 题 + 注入规则） | 学会核对了没有（得分 + 检出率 + 冗余核对率）             |
| AgentNoiseBench-τ²                         | 能否迁移到别人定义的噪声；也是和 NoisyAgent 可比的那张表 |

第三张是外部对照，用来挡"在自己造的分布上训、在自己造的分布上测"。

## 10 实现顺序（每步都有可失败的验收）

| 步骤 | 产出                                                                                             | 验收                                                                        |
| ---- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| I0   | 字段清单：对 airline 50 + retail 114 + AReaL 1711 题，列出每题可注入字段、真值定位、最短查询深度 | 清单里每个字段都能通过 §5 的检查 1                                          |
| I1   | 注入器：题 → 题变体 + 记录                                                                       | §5 的 1–3 全过；对真值字段跑检查 3 必须失败                                 |
| I2   | 检出率与冗余核对率的计算器                                                                       | 人工构造的"查了"与"没查"轨迹各一条，判定正确                                |
| I3   | **模拟器保真检查（API，无 GPU）**                                                                | DeepSeek 在三种改口条件下的实际行为：提前改口率、不改口率、自己编新值的比例 |
| I4   | 注入版 train / test 题池 + 留出划分                                                              | 查询深度分布对齐；test 的留出字段不出现在 train                             |

I3 是第一个真实验证点，也是最便宜的：它只调用户模拟器 API。如果 DeepSeek 不照 `R-on-evidence` 演（比如 agent 一问就
改口），整套设计的主设置就不成立，要先改剧本措辞。

## 11 需要决定的问题

1. **第一版的字段范围**：先只做"库中有真值的既有事实"里最容易定位的两类（订单号/预订号、在档地址），还是一上来就覆盖
   乘客数、会员等级这类需要推算的字段？推荐前者，I0 的清单先把后者标出来留给留出集。
1. **AReaL 的 1711 道题要不要进第一版**：它们的 gold 和 reward 质量参差（机械检查约 2% 确定错题，含歧义至少 6.8%）。
   推荐第一版只用官方 164 题做注入器的开发与验证，AReaL 题在 I1 通过后批量跑 §5 检查，自然筛掉错题。
1. **改口条件的实现位置**：写进单题 `task_instructions`（逐题可见、可记录），还是额外加一段注入专用的用户 prompt
   片段（更统一、但逐题差异变少）。推荐前者。
