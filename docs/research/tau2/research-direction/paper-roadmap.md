## 1 故事线

**主线（2026-10-16 定）**：

1. 交互式环境的 reward 可验证，但不可归因；
1. 我们让训练对不可靠的用户稳健，而不是去把用户做可靠；
1. 这样能扩大可训练的交互式环境的范围。

在线部署学习降为愿景，只在 intro 最后一段和 related work 最后一段出现。

工作标题：*Verifiable but Not Attributable: Training Interactive Agents with Unreliable
Users*。

先后的叙事变化：

- 2026-10-15 版：先讲"部署打破可重置和只评判 agent 这两个前提"，再收缩到不可靠用户。
- 本版改主线的原因：除推荐系统和 Cursor Tab 之外，LLM 的在线部署学习还没有被广泛证明有工业价值，论文的影响力不能押在它上面。今天离线、大规模地用模拟器训练
  agent，已经存在同样的问题。

论文正文按完整的动机链写，语气自信；证据由实验逐环补齐（§2）。自查和审稿式质疑只留在本文和 motivation review 里，不进论文。

1. **可验证但不可归因。** 交互式 agent 的训练环境里由 LLM 扮演用户，这类环境正被大规模合成（AutoForge、AReaL-SEA）。verifier
   按数据库状态判定任务是否完成，看上去和数学、代码一样干净，但结局由 agent 和用户共同产生，verifier 判不了是谁导致了结局。
1. **用户不可靠，没有干净的模拟器。**
   - 同一个 agent 只换用户模拟器，Retail 成功率从 85.0% 降到 65.0%；用户致败占失败的比例从 29% 升到 80%，agent 自身的失败数在
     10–15 之间几乎不变（图 1）。
   - 最强的模拟器下，用户仍造成 29% 的失败。
   - 真人同样不可靠：会确认后离开、改主意、记错信息。
1. **对 RL 的伤害。** 负优势落在 agent 的正确行为上，例如守规矩的写前确认。伤害有两种：
   - 用户出错与 agent 怎么做无关：信号被稀释，同样的预算学得更少。
   - 用户出错随 agent 的说法变化：策略被推向违反 policy 的捷径。
1. **主流做法是把用户做可靠，但这条路贵且不彻底。**
   - 具体做法：前沿模型扮演用户、微调用户模型、让模拟器多样化、带剧本的 judge 整条 mask。
   - 贵在两处：每条 rollout 的每个用户轮次都要调用强模型；每个合成环境都要核查。
   - 不彻底：最强模拟器仍有 29% 的用户致败。
   - 对真人无效：真人的行为改不了，也看不到其意图。
   - 组采样类方法还要求能重放同一段对话。
1. **我们的做法。** 让训练对用户稳健。设定是单条 rollout：长交互里每条 rollout 都贵，适合用单条；用户是真人时，也只能用单条。在 SAO 的
   critic 基础上，把用户回复带来的意外和 agent 自己的贡献分开计分，具体方法待定。
1. **评测原则。** 训练用不可靠用户，评测用固定的可靠用户，并直接检查 policy 合规。用模型和 persona
   构造可靠度不同的用户，并按概率注入固定缺陷做受控对照。
1. **意义。**
   - 今天：便宜、不完美的模拟器也能当训练环境，合成环境不必逐个修干净。
   - 愿景：走向从部署中学习，那里每次交互都只发生一次，对面是不受控的真人。

**成本论点的说法**：写"高保真的交互环境贵"，不写"高质量数据贵"或"专家标注贵"。理由：

- 我们的场景里贵的不是标注，而是环境：强模型扮演用户的调用成本，以及合成任务和用户剧本的核查成本。
- "高质量数据贵"太泛，审稿人会把它读成"复用脏数据"，这是我们明确不主张的。

可以借用 learning with noisy labels 的类比：便宜但嘈杂的标注因为有了稳健的学习方法才变得可用。区别在于，我们这里的噪声由另一方共同产生，并且受
agent 行为影响。引用前要先找经典文献并核实。

**其他适用场景（用户负责调研）**：结局可判定、但由不受控的另一方共同产生的环境都适用，另一方可以是用户、队友 agent，或不稳定的工具。候选：

- ColBench：协作写后端代码，单测给 reward；
- VitaBench；
- 带澄清提问的编程 agent；
- 模拟病人的诊断对话；
- 多 agent 协作。

第二个领域定下来后，回来更新 abstract 里"不限于客服"的主张。
