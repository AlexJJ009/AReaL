# 带剧本的用户错误 judge：离线验证（2026-10-18）

目的：truncate + bootstrap 方法需要一个检测器，指出"用户在第几条消息出错"。这里测带剧本的 LLM judge 在已有人工标注上准不准。 Codex
执行（pueue 619），Claude 复核。Codex 完整报告：[codex-report.md](codex-report.md)；40
条分歧复读：[audit-40.md](audit-40.md)； prompt
原文：[judge_prompts/](judge_prompts/)。服务器产物：`_artifacts/AReaL/codex-sao-math/tau2-user-error-judge-20261018/`。

## 1 设定

- **输入**：用户剧本（`user_scenario` 全字段）、用户 guideline 原文（fixed-v3，未加
  patch）、带编号的完整对话（含工具调用和返回）。 不给人工标签和 gold。
- **输出**：`user_error`、首错消息编号、类别、原文引证、置信度。
- **两个 prompt**：G 只问"用户是否违反剧本或 guideline"；G+T 在 G 后附上 U1、U3、U4/U4b、U5、U7a 的定义和例子。
- **模型**：DeepSeek 官方 `deepseek-flash`（non-thinking，T=0）全量。当时还在 200 条分层子集上用
  `deepseek-v4-pro` 做了对照；用户随后决定所有任务只用 Flash（2026-10-18），Pro 的结果不再作为依据，之后也不再调用。最初在火山订阅上跑的
  260910 部分因为和 β 训练抢额度被停掉，结果没有进入指标。
- **评测集**：v3 标注 428 条 + 普通成功 200 条；v4 标注 700 条 + 普通成功 360 条。正类为"失败且主因是 U 码"。 v4
  的标注是按题批量打的，只当近似真值。
- 参考了 AutoForge（arXiv 2512.22857）附录 A.1 的 judge：它只判断整条轨迹里用户有没有给出错误或超出范围的信息，输出
  True/False； 我们多了 guideline 和首错位置。

## 3 Claude 的读法

1. **G+T 的提升几乎都来自 U1 和 U7a**，这两类用规则就能精确检测。真正需要 judge 的是 U3（违反剧本、编造事实），这正是之前认定的
   更重要的用户错误；judge 在 U3 上只有约 57% 的召回，加 trigger 只比不加多约 10pp。
1. **误报会伤到 agent 的训练信号。** G+T 把 v3 的 63/204、v4 的 118/406 条 agent 致败轨迹（约 30%）判成用户出错。按
   truncate 的设计， 这些轨迹在判定位置之后的 agent token 会被 mask，agent 犯的错就学不到了。
1. **误报的来源**（前 20 条逐条复读）：7 条误读转接上下文（agent 已经调用了转接工具，judge 仍判用户提前 TRANSFER）；6 条是成功轨迹里
   真实存在但不致败的协议违规；4 条是 agent 先把事情做错，用户才出现问题；其余 3 条是条件授权、次数上限等误读。
1. 由此得到的检测器组合：**U1 / U7a 用规则**（精确、零成本）；**judge 只负责规则管不到的 U3 类**，prompt 收窄到"用户说的话是否与剧本
   矛盾或编造剧本外的事实"，并把转接协议从 judge 的职责里拿掉，减少第 3 点的第一类误报。

## 4 待定的问题

第二轮（规则 + 因果 judge）和规则、gold 检测器的比较见
[user-error-detectors/](../user-error-detectors/REPORT.md)。

**截断位置按"第一处用户违规"还是"致败的用户错误"？**

- 按第一处违规：judge 只需判断违规，任务更简单；但成功轨迹和 agent 先犯错的轨迹里也有违规，会多截掉一部分 agent 信号。
- 按致败的用户错误：更符合"把用户的错从 agent 的 credit 里拿掉"的本意；但 judge 还得判断因果，难度更高，目前的标注也只有致败主因、 没有逐条首错位置。

无论选哪种，都需要一批专门标注首错位置的轨迹，才能评估截断位置的准确率；现有人工引证只能当代理。
