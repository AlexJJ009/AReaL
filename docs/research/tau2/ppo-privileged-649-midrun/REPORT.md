## 0 最终结果（2026-10-20 20:44 跑完）

649 跑完 120 步，exit 0，rejected 0，checkpoint 到 `globalstep119`。第 120 步 eval：overall
52.5%（Airline 22.5、Retail 65.6、Telecom 54.4），Retail pass^4 0.40。同一步的基线 v3 是 50.5%（23.8 /

## 1 结论

1. **Retail 的提升是真的。** 第 100 步对第 0 步，按 task 配对：+17.5pp，task bootstrap 95% CI \[6.3,
   28.8\]，21 个 task 变好、6
   个变差。能看到的进步有三类：从多个订单里找到正确的对象，跨订单对齐商品属性，以及把已确认的多个子目标真的写进数据库。也有一部分成功靠的是用户纠正。

1. **Airline 不是没学，但学到的东西集中在合成 pack 上，没有迁移到原始风格的题。** 不能用"数据少"来解释：训练里 Airline 的 task 和
   episode 都比 Retail 多（410 个 task、约 8000 条，Retail 是 337 个 task、约 6600 条）。

   | Airline 训练来源 | task 数 | 早期 reward | 后期 reward | 差值 \[95% CI\]        |
   | ---------------- | ------- | ----------- | ----------- | ---------------------- |
   | pack             | 380     | 57.6%       | 69.9%       | +12.3pp \[9.1, 15.5\]  |
   | 原始 train       | 30      | 23.1%       | 14.2%       | −8.9pp \[−17.5, −0.8\] |

   Pack 和 test 题的差别很大：

   - Pack 题全部要写数据库，`COMMUNICATE` 检查为空，剧本平均 2083 个字符，gold 写参数里有 74% 直接出现在剧本中。
   - Test 题和原始 train 题相近：剧本约 600 个字符，gold 参数只有 23% 出现在剧本中；20 题里 7 题不需要写数据库（应该拒绝），还有 2
     题要求转人工。

   20 条 Airline 失败全部是 T2（违反政策或推理出错）：把改目的地当成普通改签，直接改 Basic
   Economy，退票资格和时间比较算错，金额算错。也就是说，策略学会了"更积极地执行"，但没学会"什么时候不该执行"。

1. **Telecom 的净变化≈0，是两类题方向相反、互相抵消。** 按 gold 里有没有转人工把题分成两类（Claude 独立复算过，结果一致）：

   | Telecom 题型              | 第 0 步 | 第 90 步 | 第 100 步 |
   | ------------------------- | ------- | -------- | --------- |
   | 要求转人工（12 题 × 4）   | 33/48   | 41/48    | 44/48     |
   | 要求排查故障（28 题 × 4） | 38/112  | 27/112   | 28/112    |

   - 转人工题变好，是转人工这个行为从 Airline/Retail 迁移过来了。这类题的环境目标允许保持 no_service，所以通过率上升并不代表故障被修好。
   - 排障题变差，主要原因是账户侧操作做错了线路：把开漫游、充值做到 L1001 而不是 L1002；漏掉 SMS 权限、Wi-Fi Calling 或补交账单。
   - 设备侧 gold 动作的覆盖率没有提升（432/484 → 421/484），assistant 工具报错从 48 次增加到 196 次。
   - 后期 agent 经常把工具 JSON 写在正文里，再由用户代为执行。这是输出风格变了，本身不算错误。

1. **还不能把这些现象归因到带剧本 critic。** 649 只有一个 run，没有同一用户后端下的标准 critic 对照（run 3）。

### 2.1 跟进（pueue 651）：差别在 agent 的账户操作，不在用户后端

报告：`phai:_artifacts/AReaL/codex-sao-math/tau2-telecom-crossrun-20261020/REPORT.md`（三个
run 的已保存 eval，15584 条 episode；不调用 API）。晚期窗口：基线和 631 取第 100/110/120 步，649 取第 100/110 步。

| run  | Telecom 第 0 步 | 晚期    | 变化 \[95% CI\]      | 排障题                | 转人工题 |
| ---- | --------------- | ------- | -------------------- | --------------------- | -------- |
| 基线 | 73/160          | 264/480 | +9.4pp \[1.7, 17.3\] | +12.8pp \[3.6, 21.7\] | +1.4pp   |
| 631  | 79/160          | 246/480 | +1.9pp \[−5.6, 9.4\] | +8.0pp                | −12.5pp  |
| 649  | 71/160          | 144/320 | +0.6pp \[−7.2, 8.4\] | −7.1pp \[−15.6, 0.9\] | +18.8pp  |

1. **基线的 Telecom 涨幅不完全是噪声**，但取决于窗口：只看第 120 步是 +2.5pp \[−7.5, 11.9\]。
1. **用户后端不是主因，上一节的推测不成立。** 第 0 步 policy 相同时，三个后端的 Telecom 分数差都不显著（基线 − 649：+1.3pp
   \[−6.3, 8.8\]）。agent 用 JSON 写出设备指令后，649 的用户照做的比例反而最高（晚期 95%，基线 82%，631 76%）。
1. **差别在 agent。** 排障题里，必要账户动作（给正确线路开漫游、充值、付逾期账单）的覆盖率：基线从 28% 升到 49%，649 从 26% 降到 19%。649
   晚期有约一半的排障 episode 在 gold 不要求时转人工（Claude 复算第 100/110 步为 63/112、53/113），基线晚期约 29%（第
   100/110/120 步为 27/113、36/112、34/112）。也就是说，基线学会了把账户侧的故障修完，649 学会的是放弃并转人工。
1. **还不能归因到带剧本 critic。** 两个 run 同时在用户后端、训练用户、critic、并发数（128 对 24）上不同。需要同一用户后端下的标准 critic
   对照（run 3）才能分开。
