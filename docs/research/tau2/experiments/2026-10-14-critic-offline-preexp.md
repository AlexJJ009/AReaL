## 1. 目的

critic-only 训练（479、499、510）的验证 EV 一直接近 0。case study 的判断是 Airline 有可学的信号、critic
欠拟合，但没有做过干预实验。本实验在冻结的骨干网络特征上做离线分析，回答"修 critic 应该先改什么"：学习率、batch 大小、标签噪声，还是骨干网络本身的特征不够。

全部实验不调用 API、不启动 SGLang 和用户模拟器。只有特征提取需要 GPU，其余在 CPU 上完成。

## 2. 背景

- 当前 head：$V = w^\top h + b$，$w$ 零初始化，$b$ 初始化为标签均值，head 和骨干网络 lr 都是 5e-6，Adam，每步 16
  条轨迹，`ppo_n_minibatches: 1`。
- 510 训练完 $\|w\| \approx 0.0024$，499 为 0.0015。按 Adam 每步每个参数最多移动约 lr 估算，80 步的上限约为
  $80 \times 5\text{e-}6 \times \sqrt{2560} \approx 0.02$，实际只到上限的 6–12%。
- $w$ 很小时，骨干网络的更新对预测的影响是 $w^\top \Delta h$，也很小。所以零初始化的 head 同时限制了骨干网络的作用。
- 词袋分类器在 Airline 上 EV 0.24（五个前缀长度平均），高于 critic 的 0.02–0.17。
- SAO 论文的 critic：lr 5e-6，每步 128 条轨迹，每步 2 次 critic 更新，先做 critic-only 预训练。

## 5. 公共设置

### 5.1 数据池（已由数据核对确定）

数据核对（pueue 538）的报告和清单在产物目录 `data-audit/`：`report.md`、`pool-manifest.json`（sha256 见同名
`.sha256` 文件）。所有实验只读取这份清单，不再自行挑选数据；读取时校验 sha256。

**训练池：r499 + r510，2774 条。** 两个 run 的 actor、用户模拟器、NL judge、benchmark
变体（fixed-v3）、计分代码和训练题定义都一致；r510 的 pack 是 r499 所用 pack v2 的子集，题目定义和数据库逐题相同。

| 领域    | 轨迹 | 成功 | 失败 |
| ------- | ---- | ---- | ---- |
| Airline | 1540 | 1266 | 274  |
| Retail  | 1234 | 1149 | 85   |
| 合计    | 2774 | 2415 | 359  |

- 320 道题各有 6 条轨迹（r499 2 条 + r510 4 条），另外 427 道题只在 r499 出现，各 2 条。按轨迹平均时，前者每题的权重是后者的 3 倍；这
  320 道题又是按 r479 的结果挑出来的偏难题。所有实验保留 run 和题号，结果按"全部轨迹"报告，需要时再按题加权对照。
- 保留 3 条超出预算的轨迹（r499 `airline:10`，r510 `airline:10`、`airline:23`），按原协议记 0 分。
- **r479 不进入训练池。** 它的训练题和数据库与后两个 run 一致，fixed-v2 与 fixed-v3 的差别只在 7 道验证题上；但它启动时没有固定
  `PYTHONPATH`，实际加载的代码来源无法完全确认，保守起见整体排除。
- **主数据**（E3 复现真实训练）：r510 的 1280 条，按 510 实际的 batch 顺序。

**主验证集：r499 + r510 的验证集合并，120 条**（60 道 test 题每题 2 条；Airline 40 条、失败 16，Retail 80 条、失败
14）。两份是分别采样的，同一题的两条轨迹不同。r479 的验证集用 fixed-v2，不并入。训练池与验证集没有重复的题。验证题不进入任何拟合，包括选超参数。

**用户模拟器的口径**：用户和 NL judge 都没有显式关闭 thinking，保存的回复里有 reasoning token，配置中的 temperature 0
实际不生效。这些数据不能当作"用户确定性"的数据，E6 的解读需要考虑这一点。

### 5.2 指标

- **EV**：直接调用验证报告用的函数（`evaluate_tau2_critic` 或它内部的 EV 计算），不另写一套。分
  Airline、Retail、总体报告，同时报告偏移。
- **AUC**：用每条轨迹所有 action token 预测的平均值排序。
- **区间**：把 60 道题作为分组单位，有放回抽题，同一题的 2 条验证轨迹一起进出，2 万次。比较两个设置时用配对 bootstrap，即两者共用同一组抽样。
- **验证集**：5.1 的 120 条主验证集。另外分别报告 r499、r510 各自 60 条上的结果，作为参考。

### 5.3 超参数选择

ridge 的正则系数、模拟中的"最优 lr"都只能在训练数据上选。做法：按题分组做 5 折交叉验证，同一道题的所有轨迹只出现在一折里。不允许用验证集选。

### 5.4 随机性

种子统一为 20261014。每个模拟设置跑 3 个种子（影响 batch 抽样顺序的设置除外，E3 复现 510 时 batch 顺序固定），报告均值和范围。

## 6. 实验步骤

### E1 特征提取（GPU，1 卡）

| 设置             | 值                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------- |
| 骨干网络         | 原始 Qwen3.5-4B；510 第 55 步 critic 的骨干网络（只取最后一层，供 E7）                       |
| 层               | 最后一层（value head 的实际输入，需有测试证明逐元素一致）+ 约 25%、50%、75% 深度的三个中间层 |
| 训练轨迹的 token | 每条轨迹在 action token 中均匀抽 128 个（种子固定），记录位置、所在轮次、题号、领域、reward  |
| 验证轨迹的 token | 全部 action token，以便精确复现验证口径                                                      |
| 精度             | bf16 存储                                                                                    |

只提取 5.1 清单里的轨迹（约 3100 万 token）。开始前写出时间和磁盘估计；可以在 8 张卡上按轨迹分片并行，合并后校验条数和清单一致。

### E2 闭式探针（CPU，检验 H1）

1. 在最后一层特征上做 ridge 回归，目标是 0/1 reward，正则系数按 5.3 选。
1. 分别报告：两个领域共用一个探针；每个领域单独一个探针。
1. 同时做逻辑回归探针（sigmoid + BCE），报告 EV 和 AUC，作为损失函数的对照。
1. 输出验证集 EV、AUC、偏移、区间，以及探针权重的范数，和 510 的 $\|w\|$ 对比。

### E3 只训 head 的 Adam 模拟（CPU，检验 H2、H3）

模拟只训 head、骨干网络冻结，所以它是"只调 head 学习率"的效果，不包括骨干网络的变化。

| 设置    | 值                                                    |
| ------- | ----------------------------------------------------- |
| 数据    | r510 的 1280 条，按 510 实际的 batch 顺序，每步 16 条 |
| 损失    | 与训练器相同的 token 级 MSE 和加权方式                |
| 初始化  | $w = 0$，$b$ = 510 的初值 0.78                        |
| head lr | 5e-6、2e-5、1e-4、3e-4、1e-3                          |
| bias    | 可学；固定在初值                                      |
| warmup  | 无；前 10 步线性 warmup                               |
| 步数    | 80，每 5 步在验证集上评估一次                         |

先跑 lr 5e-6、bias 可学、无 warmup，判定 H2。H2 不成立时，后面的模拟结果只能作为参考，结论里要写明。

### E4 batch 大小与训练量（CPU，检验 H4）

回答"每步 128 条有没有用"。在线做 128 条一步的代价是每步 API 成本变成 8 倍，所以先在离线数据上看效果。

| 设置                 | 值                                                 |
| -------------------- | -------------------------------------------------- |
| 数据                 | 5.1 确定的数据池                                   |
| batch                | 16、64、128                                        |
| head lr              | 按 5.3 在训练数据上选出的最好的两个 lr，以及 5e-6  |
| 训练量 A：样本数相同 | 都看 1280 条，batch 16/64/128 分别对应 80/20/10 步 |
| 训练量 B：步数相同   | 都跑 80 步，batch 128 时约等于在训练池上过 3.7 遍  |

报告每种组合的 EV 曲线、$\|w\|$、偏移跳动。训练量 B 要额外报告训练集 EV，看重复使用数据有没有过拟合。

### E5 梯度一致性（CPU，检验 H4）

在 E3 的 lr 5e-6 设置下，记录每步 head 梯度：

- 相邻两步梯度的余弦相似度，以及每步梯度与"全部数据上的梯度"的余弦相似度；
- 每个坐标的梯度符号在 80 步中保持一致的比例；
- 按 batch 大小 16、64、128 重复上面两项。

预先约定的解读：每步梯度与全量梯度的平均余弦 \< 0.1，说明 batch 16 的梯度基本是噪声；batch 128 时如果升到 0.3 以上，支持 H4。

### E6 软标签（CPU，检验 H5）

把每条训练轨迹的标签从 0/1 换成"这道题在训练数据里所有轨迹的平均成功率"，其余设置同 E2，以及按 5.3 选出的最好的 lr。验证时仍然用真实的 0/1 结果算 EV。

解读：软标签去掉了同一道题内部的随机性，也去掉了这条轨迹自己的信息。如果它反而更好，说明 0/1
标签里的题内随机性（[EV 上限实验](../critic/ev-ceiling.md)显示主要来自用户一侧）是 critic 训练的瓶颈，这会作为论文 motivation
的证据。训练池里每道题有 2 条或 6 条轨迹，只有 2 条的题平均成功率只能取 0、0.5、1，比较粗；结果要按这两类题分开报告一次。

### E7 特征的层和位置（CPU，检验 H6、H7）

1. 对 E1 的每一层做 E2 的 ridge 探针，比较验证 EV（H6）。
1. 用 510 第 55 步骨干网络的最后一层特征做同样的探针，与原始模型比较（H7）。
1. 按位置分组报告最后一层探针的 EV：第一个 action token；轨迹进度 0–20%、20–40%、…、80–100%。这能看出信号在对话哪一段出现，以及
   Retail 是否只在后段有信号。

### E8 植入信号（CPU，检验 H8）

1. 从轨迹文本中定义一个能直接看到的二值标签，例如"本轮之前是否有工具返回包含 `Error`"。先统计它在训练集中的比例，要求在 20%–60%
   之间；不满足就换一个规则，并在第 9 节记录换了什么、为什么。
1. 用这个标签替换 reward，跑 E2 的 ridge 探针和 E3 的 lr 5e-6 模拟。

解读：如果探针能学会、模拟学不会，说明当前设置下 80 步、5e-6 的优化预算连简单信号都不够，问题和数据无关。

### E9 LP-FT 准备（CPU，不训练）

把 E2 中在训练数据上选出的最好的探针，导出成 critic head 的初始权重（$w$、$b$），写成可被 `offline_critic_fit.py` 和 SAO 的
`check_critic_head.py` 读取的格式，并验证读回一致。这是之后"先拟合 head、再训练整个 critic"实验的起点，本实验不跑。

### 偏离协议

1. **E8 的植入标签。** 原计划：用"本轮之前是否有工具返回包含 `Error`"这类可见规则，比例要求 20%–60%。

   - 第一版实现把 system prompt 也算进去：Retail 的 1234 条轨迹 prompt 里全部含 `error`，Airline 只有 6/1540
     条，标签实际等于领域。合计比例 46.8%
     看起来达标，是因为只检查了合计，没有分领域。这一版作废（`planted-rule.domain-confounded.json`）。
   - 修正为只看 initial prompt 之后完整结束的工具返回后，`error`、加上 `not found`、再加上 `invalid` 和 `cannot`
     三个候选的比例都约为 5%（`planted-rule.tool-return-error.json`），不达标。
   - 实际采用：**之前 agent 是否已完整调用过写操作工具**。写操作工具从固定版本 τ² 源码的 `ToolType.WRITE` 标注自动提取（Airline 6
     个，Retail 7 个），`transfer_to_human_agents` 属于 GENERIC，不计入。训练集比例合计 24.9%（按 token 计
     29.2%），Airline 22.4%，Retail 28.1%。验证集合计 19.0%，只作记录，不参与筛选。
   - 新增检查：比例必须分领域满足 5%–95%，避免标签退化为领域标签；该检查和规则语义都有测试，撤掉后测试变红。
   - 原因：原规则在真实数据里太少见。H8 的判据不变。

1. **E1 的抽样。** r499 `retail:83`（`1429.jsonl`）只有 45 个 action token，无法不放回地抽 128 个，全部保留；其余
   2773 条各抽 128 个，训练特征共 354,989 行。

1. **E2 的主口径。** 协议同时要求两个领域共用一个探针和每个领域各一个探针，没有指定判定 H1/H5 用哪一个。执行前定为：以共用探针为主，分领域结果作参考；E9
   导出共用探针。

1. **H3 的比例判据。** E2 探针 EV ≤ 0 时，"达到探针 EV 的 70%"没有意义，此时 H3 不判为成立。

1. **E6 的分组。** "2 条 vs 6 条"指训练题按轨迹数分两组，分别拟合，在同一份验证集上评估。
